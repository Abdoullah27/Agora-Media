1. PRIMARY GOAL OF THE PROJECT
--------------------------------------------------------------------------------

The Agora Growth Engine is a premium, high-conversion web platform built for
"Agora Media," a digital marketing agency. The primary goal is to transition the
agency's static marketing footprint into a dynamic, performance-driven web
application that serves three core missions:

  a) LEAD GENERATION: Capture qualified client leads through a fluid, accessible
     contact form and marketing-optimised UX patterns (countdown banners,
     sticky CTAs, social proof sections).

  b) PORTFOLIO SHOWCASE: Display the agency's creative work (Social Media,
     Reels, Websites, Branding, 3D content) in a visually striking, filterable
     masonry gallery to convert visitors into clients.

  c) INTERNAL CONTENT MANAGEMENT: Empower non-technical team members to manage
     website content (upload projects, edit descriptions, manage images) through
     a built-in Admin CMS panel — without touching any source code.

In summary, the website functions as a 24/7 sales engine: attracting traffic,
building credibility, and converting visitors into leads for Agora Media.

5. PERFORMANCE AND SPEED
--------------------------------------------------------------------------------

OPTIMIZATIONS IMPLEMENTED:

  a) Particle Grid Algorithm Upgrade:
     - BEFORE: O(n²) brute-force comparison — every particle checked
       against every other particle (240+ comparisons per frame at 60fps)
     - AFTER: Spatial grid partitioning — only 3×3 neighboring cells
       are checked (~10 comparisons per frame)
     - RESULT: 50–70% canvas animation performance improvement
     - Now maintains stable 60 FPS even on large/4K screens

  b) React Component Memoization:
     - MagneticCursor wrapped with React.memo() — prevents unnecessary
       re-renders as the cursor is always mounted at the root level
     - Eliminates cascading re-render costs on every mouse move

  c) Lazy Loading (Code Splitting):
     - Heavy routes loaded on demand via React.lazy():
         /portfolio, /portfolio/:slug, /pricing
         /insights, /insights/:slug
         /admin, /admin/dashboard
     - Reduces initial bundle size — home page TTI is minimal
     - Webpack chunk names assigned for debugging network tab

  d) Canvas Animation Pause:
     - ParticleGrid and Sparkles use useInView hooks
     - requestAnimationFrame is cancelled when components scroll
       out of the viewport — saves mobile battery and GPU cycles

  e) Bundle Cleanup:
     - @tanstack/react-query removed (was unused, saved ~20KB)

  f) Performance Monitoring:
     - use-performance-monitoring.ts hook tracks Core Web Vitals:
         LCP (Largest Contentful Paint)
         FID (First Input Delay)
         CLS (Cumulative Layout Shift)
     - PerformanceObserver API used for accurate measurement

8. CURRENT CHALLENGES
--------------------------------------------------------------------------------

  1. NO REAL BACKEND YET
     The most significant limitation: all CMS data lives in the
     browser's localStorage. This means:
       - Data is lost when the browser cache is cleared
       - No multi-user or multi-device access
       - Image storage limited to browser localStorage quota (~5MB)
     Resolution path documented in docs/API_INTEGRATION.md (Supabase
     or Firebase recommended for the backend migration).

  2. FORM SUBMISSION NOT FULLY LIVE
     The contact form runs in "simulator mode" if VITE_LEAD_WEBHOOK_URL
     is not configured. A webhook endpoint (Make.com, Zapier, or a
     custom server) must be set up and configured in .env.local.

  3. E2E TESTS NOT YET WRITTEN
     Playwright is installed and configured, but end-to-end test
     scripts have not been authored. Critical unit tests (Vitest)
     cover form validation, FAQ, and navigation (20+ tests), but
     full user-flow testing remains undone.

  4. UNUSED DEPENDENCIES
     - Recharts (recharts 2.15.4) is in the bundle but may not be
       used actively — should be audited and removed if unused to
       reduce bundle size.
     - Multiple Radix UI components installed that may be unused.

  5. CSRC TOKENS NOT IMPLEMENTED
     The backend (when created) will need CSRF token protection.
     Strategy is documented but not yet buildable without a backend.

  6. FEATURES NOT YET DEPLOYED TO PRODUCTION
     The project is development-complete but has not been deployed to
     a live hosting environment (Vercel, Netlify, Cloudflare Pages, etc.).

  7. FACEBOOK PIXEL NOT CONFIGURED
     VITE_FB_PIXEL_ID is empty in the example env file. The pixel
     will silently skip tracking until the team provides a real Pixel ID.
